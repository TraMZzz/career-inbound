# On-call Copilot — опис проєкту

## Проблема
Черговий інженер отримує алерт уночі й витрачає перші 10–20 хвилин на те, щоб зрозуміти, де саме проблема:
алерт приходить на сервіс, який бачить симптом, а причина часто в залежності (БД, кеш, зовнішній провайдер,
свіжий деплой).

## Користувач
Бекенд-інженер на чергуванні, який знає систему загалом, але не памʼятає кожен сервіс напамʼять.

## Що робить AI-частина
Отримує текст алерту, збирає релевантні логи, метрики й деплої, пропонує:
категорію збою, сервіс-причину, докази (посилання на рядки логів), наступні кроки
і, за потреби, дію (рестарт, відкат), яку підтверджує людина.

## Як виміряти, що це працює
- **Головна метрика:** `pass_rate` golden set (`ci-eval run`): для алертів copilot правильно називає категорію збою
  і сервіс-причину (для поганого деплою ще й пропонує відкат), для не-алертів чесно каже `unknown`.
  Ціль: 0.8+ (переглянути після першого baseline).
- **Допоміжні:** latency p95 відповіді (ціль: до 15 с) і вартість на 1000 алертів — `make eval` показує їх
  з уроку 2, свідомо оптимізуємо в уроці 7.
- **Безпека:** 0 незворотних дій без підтвердження людиною (`ci-eval attack`).

## Обмеження
- Дані синтетичні (demo-shop), але формати логів імітують реальні бібліотеки.
- Copilot нічого не виконує сам: лише `actions_proposed` з `requires_confirmation: true`.
- Відповідь має посилатися на реальні рядки логів; вигадані id відкидаються.
